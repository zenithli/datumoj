# 容量预算：离线设计与可运行测试

对应 [统一指令板 #4](https://github.com/zenithli/datumoj/issues/1#issuecomment-6806340654)。这是独立的可执行设计说明，不是生产限流器，也不接入当前采集、发布或清理路径。没有修改 PR #173。

## 1. 目标与边界

给定同一计量范围中互不重叠的前缀字节、按顺序排列的预计新增写入、随后发生的假设清理事件及阈值，输出每轮写入前总量、写入后峰值、清理后总量和三阶段阈值余量。

只用写入后峰值判断是否达到或超过阈值。清理的字节只能在清理事件之后扣除，不能为本轮前面的写入提供额度。下一轮可使用前轮清理后的余额，但这仍以该清理实际完成为条件；实际部署必须重新盘点，不能把模型结果当作事实。

函数不访问文件、网络、环境变量、时钟或凭据，不修改调用方输入。测试只使用合成对象身份和数值。它不能证明候选存在、符合保留策略、已归档、获得删除许可或能安全恢复；也不执行删除、批准写入或推导账户总量。

## 2. 设计选择

- 采用独立的纯函数模型与标准库测试，便于审查方在离线环境直接重算。
- 不把模型嵌入 PR #173，也不新增云端命令或工作流。PR #173 负责观测，模型负责给定输入下的条件计算。
- 不使用“当前总量 + 新增 - 预计清理”直接判阈值，因为它会隐藏清理前峰值。
- 不只输入一个清理字节总数。清理计划提供物理对象身份、所属前缀和大小，用身份去重，避免多个代次对同一 raw 的引用重复扣减。

所有大小均为精确的非负整数 byte，1 GB = 1,000,000,000 B。拒绝负数、浮点数及 bool，避免负清理、截断或浮点精度悄悄改变结果。

输入类型不符抛TypeError；非法数值、字段、未知分类、身份冲突或前缀透支抛ValueError。显式传入阈值映射会完整替换默认值，空映射会关闭阈值报告，不代表容量安全；省略该参数才使用默认三条阈值。

### 输入

`project_capacity(current_prefix_bytes, rounds, thresholds=None)`。

- `current_prefix_bytes`：前缀或分类标签到字节的映射。各项必须属于同一快照、同一范围、互不重叠。该条件由数据提供方保证；聚合数字本身不能证明范围完整。后续写入或清理使用的分类必须在此声明，新分类可先声明为0，拼错或未知分类不被静默接受。
- 每个 round 的 `writes_by_prefix`：该轮预计新增的唯一物理对象字节。它不是 HTTP 下载字节、逻辑引用字节、过去清理后的净增量，也不是已经扣过预计删除的值。迁移时旧新副本并存和失败遗留对象都要计入。
- 每个 round 的 `cleanup`：假设届时符合全部条件并成功删除的对象。每项提供 `object_id`、`prefix`、`size_bytes`。身份指计量范围内的物理对象实例，不是代次编号或引用行。跨 bucket 的同 SHA 是不同物理对象，不能合并；同一对象在多个已退役代次中的引用则只能扣一次。
- 同一身份在同轮或跨轮重复出现，只在首次模型清理时扣减。相同身份却给出不同大小或前缀时拒绝输入。若删除后重新创建同一 key，需要由提供方给出新的实例身份；只有聚合写入量无法自动推断重建。同一旧身份再次出现不会再次释放空间。
- 默认阈值为 7,000,000,000、8,500,000,000、9,000,000,000 B。若需同时报告 8GB 确认线，须显式传入包含四条线的完整映射。默认三条来自 #4 的模型范围，不替代仓库的其他规则。

清理对象的成员资格和保留引用无法由前缀总数验证。本模型把清理计划视为显式情景假设，只检查身份一致性和前缀余额不被扣成负数。无真实候选清单时应使用空清理计划，而不是给未知对象制造身份以抵扣容量。

### 输出与计算顺序

每轮依次计算：

1. `before = sum(当前各前缀字节)`。
2. 对各前缀加预计新增写入，得到 `write_peak`。
3. 对假设清理对象去重后扣减，得到 `after_cleanup`；不允许前缀余额透支，不静默截成 0。
4. 对每条阈值，分别计算写入前、峰值和清理后余量 `threshold - total`，保留负数。
5. 所有阈值状态仅从 `write_peak` 导出：`reached` 是 `>=`，`exceeded` 是 `>`。峰值恰好等于阈值时，余量为 0，reached=true，exceeded=false。达到预警、冻结或停写阈值不能被当成“尚未严格超过所以安全”。
6. 下一轮从上一步余额开始。全情景最高值包含初始总量及每轮写入峰值，后来的清理不会抹去它。

没有轮次时仍返回初始总量及以它为起点的最高值。零写入和空清理是正常边界，不意味着当前库存变成零。输出的最高值是本次情景的推算值，不是过去已经发生的历史高水位。

## 3. 四项必需测试与具体错误变异

所有期望值手算为固定整数，不调用被测函数生成期望。

| 场景 | 输入与期望 | 应被抓住的具体错误 |
| --- | --- | --- |
| 清理不能掩盖峰值 | 初始90，写30，随后清40，阈值100：写前90、峰值120、清理后80；峰值余量-20，达到及超过均为真 | 用清理后80而非峰值120判断阈值 |
| 同 raw 多代引用 | 初始100，同一30字节对象出现两次：仅清30、剩70；后轮重复该身份仍剩70 | 按两条引用扣60，或后轮再扣30 |
| 空清理、零写入 | raw10、copies20，无写入无清理：三个总量均30，距100余70 | 无写入时把现有库存归零 |
| 等于阈值 | 初始90、写10、清20、阈值100：峰值100，余量0，reached真、exceeded假 | 把reached的>=改成> |

`check_mutations.py` 会对独立临时版本真正施加上述四种错误，并执行对应行为测试。只有预期断言失败才算捕获，语法或导入异常不算。原模型不被改写。实际运行结果见 `verification.json`。

补充测试覆盖跨轮余额、最高值保留、重复身份冲突、不同物理对象、透支、非法数值、超过2**53的精确整数、自定义阈值和输入不变性。

## 4. 如何消费 PR #173 的只读盘点

核对版本：[PR #173](https://github.com/gorou5/datumoj/pull/173)，head `ef32c684b4d4db929aab5fc500b0d23d703384b7`。以下是接入设计，没有修改或运行该PR，也没有从云端取得新盘点。

成功结果中可用字段是：

```
scope: "this_bucket"
total: {objects, bytes}
prefixes:
  generations: {objects, bytes}
  copies: {objects, bytes}
  raw: {objects, bytes}
  other: {objects, bytes}
headroom_bytes: {"7gb", "8_5gb", "9gb"}
```

成功结果没有必需的exit_status字段；失败结果为包含exit_status=1、phase、reason的对象，不能用作零库存。见 [capacity.py38–94](https://github.com/gorou5/datumoj/blob/ef32c684b4d4db929aab5fc500b0d23d703384b7/src/datumoj/rikolto/capacity.py#L38-L94)、[cloud.py550–632](https://github.com/gorou5/datumoj/blob/ef32c684b4d4db929aab5fc500b0d23d703384b7/src/datumoj/rikolto/cloud.py#L550-L632)。

未来只读适配步骤：

1. 消费已经保存的JSON，不在本模型中创建S3客户端或运行盘点命令。拒绝失败结果、缺字段、bool/浮点/负数计数。
2. 验证四个prefix分类的字节及对象数分别加总为total，然后把四个bytes字段作为初始映射。现有headroom只用于一致性检查，不再加进容量。
3. 单独补充同范围的观测时间和来源标识。相同的"this_bucket"字符串不能证明两份快照来自同一个桶。
4. 单独提供每轮预计新增物理字节和清理对象情景。保持清理后才获得容量的顺序。

不能把stores、generations[*].referenced_bytes、current_generation或raw_sources再次加到prefixes上：它们是同一库存的其他观察维度，部分存在跨代次或跨逻辑库重叠。exclusive_bytes也不代表对象已获准清理。reclaimable只是盘点时的候选统计，不是实际删除，也不含可用于跨轮去重的对象身份；raw_enabled=false时原始候选统计也未必归零。

PR #173 的范围是整个配置桶。配置命名空间以外的对象归other，即使它们在其他命名空间下也有raw/或copies/前缀。日期分组不在该输出中，不能与按LastModified日期的库存直接换算。稳定的current指针检查也不等于冻结全桶对象变化。

### 缺少的输入

- 每轮预计新增唯一物理对象字节，包括raw、缺失副本块、索引、代次清单、其他对象、迁移并存、上传失败遗留及并行写入；需要来自另行授权的离线计划/样本测量或未来实际写入计量，不能由历史净增直接替代。
- 按对象身份、大小及前缀列出的清理候选，以及届时仍成立的保留引用、72小时、归档和许可条件。函数不计算这些条件。
- 盘点时间、桶与命名空间来源、账户中其他桶/写入者、并发与在途变化。
- 如果预计新增只是点估计而非可证明上界，模型只能给出情景，不能保证不越线。安全余量或未知开销必须显式纳入预计写入，不能默认为零。

PR #173目前的工作流把JSON写入运行日志和摘要，没有上传独立artifact。[cloud-usage.yml37–48](https://github.com/gorou5/datumoj/blob/ef32c684b4d4db929aab5fc500b0d23d703384b7/.github/workflows/cloud-usage.yml#L37-L48)。本交付不触发工作流，只说明未来如何消费已保存输出。

## 5. 手算情景和范围声明

`examples.py` 提供可重算的合成例子；`example_results.json`是该脚本的离线输出。

真实来源只作为给定基线：[验收 #3](https://github.com/zenithli/datumoj/issues/1#issuecomment-6782541584)报告2026-11-11 08:30 JST桶总量8,800,774,448 B。它是板上报告，不是本次重新测量，也不是已知账户总量。raw约4.30GB、副本约4.50GB、清单约35MB是舍入数，不能据此伪造能精确相加的前缀明细，因此例子仅把准确桶总数作为一个聚合分组。

假设之后新增250,000,000 B，再清理一个600,000,000 B合成对象：写前8,800,774,448，峰值9,050,774,448，清理后8,450,774,448。虽然清理后低于8.5GB，峰值已超过9GB 50,774,448 B，不能因此宣称本轮写入可行。新增和清理数字都是假设，不是现有盘点可证明的量。

下一轮若新增49,225,552 B，峰值恰好8,500,000,000。重复列出同一个已清理对象不会再次腾空间；全情景最高值仍为9,050,774,448。

在此目录运行，Python 3.12及以上，只有标准库依赖：

```
python check_mutations.py
python examples.py
```
